# this/that 整体改进对比报告

日期：2026-09-22，Asia/Shanghai。

范围：汇总 Botanic O5 从业务意图分类、检索来源选择、候选重排，到工具搜索和工具选择 V2 的五轮实验。本报告不是整个产品的代码优化验收，也不替代在途 Turn 发布兼容性报告。此次只核对已有文件并整理报告，没有追加模型请求、修改生产代码或发布。

## 1. 总结：提升在哪里，没有提升什么

**最明确的改善是：同一批新题上，工具选择更少漏掉必要能力。还没有证据证明完整 Agent 更快、更省钱或执行成功率更高。**

| 维度 | 已验证结果 | 不能据此得出的结论 |
| --- | --- | --- |
| 工具选择召回 | 同题 V1→V2：12/21→20/21，57.1%→95.2% | 不能说完整任务成功率达到95.2% |
| 多工具需求完整性 | 必要工具全部选齐的任务：6/13→12/13 | 不能说参数、执行顺序和依赖都正确 |
| 工具建议精确性 | 模型独立精确率100%→83.3%，更多多选；加同一状态规则后V2为87.0% | 不是所有准确性指标都变好 |
| 已召回候选的排序 | 受控候选池正例首位命中5/12→12/12；含3次原序回退贡献 | 不能说模型独立匹配率100%，也不是完整检索召回率 |
| 分类输入效率 | 同题工具选择输入token减少45.6% | 不等于总费用或总计算量减少45.6% |
| 用户等待时间 | 工具分类每题中位数2.00秒→1.99秒，基本未变 | 没有测得可用的端到端提速结论 |
| 生产可用性 | 独立离线实验与建议选择器已交付；未接生产 | 不能说正式Agent已获得上述提升 |

本次没有训练或微调模型权重。改变的是**任务拆法、问题表达、输入内容和外围选择规则**，所有真实分类均使用 FLock `this-that-model-1.0`。Jev 是另一服务，未调用，不能把这些结果归给 Jev。[S1–S5]

### 指标如何读

- **必要工具选中率/召回率**：应选的工具有多少被保留。16个留出任务累计21项必要工具需求，不是目录中有21种工具；合成目录只有8种。
- **建议精确率**：选出来的工具里，有多少确实是任务必要的。召回高但精确率低，意味着漏得少、选得多。
- **全部必要工具选齐**：一项任务的必要能力都在建议里，允许还有多余项；不等同于“不多不少”或“实际执行成功”。
- **精确集合**：不漏选也不多选；仍不验证参数、次序或执行。
- **p50/p95**：客户端耗时的中位数/95分位，包含网络与服务响应；不是模型裸推理耗时。

## 2. 五轮实验总览

以下是研究过程，不是一条可以直接相减的统一准确率曲线：不同轮次的任务、数据、选项和指标不相同。

| 轮次 | 实际测试的问题 | 数据与主推理请求 | 主要留出结果 | 当前判断 |
| --- | --- | --- | --- | --- |
| ① 六类业务意图 | 对话、Prompt、检索、生成、行动提议、未知 | 240条中英合成样本；240次；留出120条 | accuracy20.0%，macro-F1 0.168；86.7%输出unknown；本地提示信号accuracy39.2% | 不适合作为当时配置下的总路由替代 |
| ② 检索来源 | 当前画布、历史产物、已保存规则、交回Planner | 48条合成样本；开发4版本+留出1版本，共120次；留出24条 | 原始11/24正确；包装层后10/24，18/24回退 | 提供状态有局部帮助，但来源选择仍不可靠 |
| ③ 候选匹配/重排 | 已有候选是否符合请求 | 30个查询×3候选，90次；留出18个查询 | 有答案查询首位命中5/12→12/12；模型主动认出9/12；无答案误接受1/6 | 有排序收益，未通过拒绝错误候选的门槛 |
| ④ 工具搜索V1 | 每个工具是否必要、无关或信息不足 | 24个任务×8工具，192次；留出16个任务 | 必要工具召回8/19；全部16题退回完整目录；目录缩减0% | 不适合裁剪目录 |
| ⑤ 工具选择V2配对 | 逐项判断是否需要该能力，状态规则分开 | 24个新任务×8工具×2版本，384次；留出16个任务 | 同题召回12/21→20/21；精确率100%→83.3%；输入token下降45.6% | 更适合继续作为建议层研究，尚不准入自动执行 |

五份JSON保存了 **1,026条主推理结果**，均无记录中的中断。第一轮另记有1次smoke和4次协议控制题，按现有实验记录合计 **1,031次推理调用**，不含报价查询。1,031次调用不是1,031个独立用户任务；同族中英表达、同题候选/工具和版本对照相互关联。前两轮的一些汇总没有逐次usage，不能拼出完整调用链的统一token/费用总账。[S1–S5、D1–D5]

### 哪些比较可以当作提升证据

1. **可以：最新V1/V2同题配对。** 同一请求、同一已知事实、同一工具目录、同一Gold，调用交错，比较必要工具集合。[D5]
2. **可以，但有边界：同一受控候选池原序与重排。** 只说明已召回候选的排序变化，不说明从完整项目找回了更多记录。[D3]
3. **只限开发集：检索来源有状态/无状态对照。** 相同问题和选项下，描述版有状态16/24正确，无状态10/24；不是留出提升，更不能推广成“状态解决了问题”。[S2]
4. **不可以：20.0%→45.8%→95.2%当成总准确率进步。** 三者分别是六类意图accuracy、来源accuracy、工具召回；分母不同。
5. **不可以：工具V1上一轮42.1%直接与V2这轮95.2%相减。** 新题上重新测得的V1是57.1%，这是本轮应使用的基线。

## 3. 重点：工具调用选择改进了多少

### 3.1 模型独立的同题结果

16个留出任务，其中13个需要工具，3个无需目录中的工具；累计21项必要工具需求。两臂各调用128次，不含状态规则补救。

| 指标 | V1 | V2 | 变化 |
| --- | ---: | ---: | --- |
| 必要工具召回 | 12/21，57.1% | **20/21，95.2%** | +38.1个百分点 |
| 漏选数量 | 9 | **1** | 少漏8项 |
| 必要工具全部选齐的任务 | 6/13，46.2% | **12/13，92.3%** | 多6个任务选齐 |
| 建议精确率 | 12/12，100% | 20/24，83.3% | −16.7个百分点 |
| 多余建议 | 0 | 4 | 增加4项 |
| 精确集合 | 9/16 | 11/16 | 多2题不多不少 |
| 无需工具却建议了工具 | 0/3 | 1/3 | 出现退步 |
| 只读请求误建议写/计费/删除工具 | 0/7 | 0/7 | 本小样本未观察到 |

直白说：**旧版过于保守，很多该用的工具没选；新版更会把任务所需能力找齐，但会顺带多选几个。** 不能只报95.2%，不报83.3%的精确率和无工具误选。[S5、D5]

### 3.2 状态规则不是模型能力

对于“删除目标不明”“生成主题未给”两个样本，已有合成状态明确标注缺少用户输入。两臂都应用同一个先澄清的规则：

| 指标 | V1 + 同规则 | V2 + 同规则 |
| --- | ---: | ---: |
| 必要工具召回 | 14/21，66.7% | 20/21，95.2% |
| 建议精确率 | 14/14，100% | 20/23，87.0% |
| 正例任务全部必要工具选齐 | 8/13 | 12/13 |
| 精确集合 | 11/16 | 12/16 |

规则帮V1补回两个澄清工具；V2本身已选中这两个澄清工具，规则只去掉一次过早生图建议。剔除这两个依赖给定缺参状态的任务后，其余14题的模型召回仍从 **12/19（63.2%）升至18/19（94.7%）**。

这些状态是样本人工给定的前提，**上游如何准确获取它们未测**。现有简化把一个整体受阻请求先交给澄清；不能直接用来阻塞复杂任务里本来可独立推进的步骤。[S5；`evalAgentToolChoiceO5.mjs`的`chooseTools`]

### 3.3 多步骤案例

| 合成请求 | V1 | V2 |
| --- | --- | --- |
| 同时找当前画布和历史产物 | 只选画布 | 两种都选齐 |
| 读材质规则并查任务排队情况 | 两种都漏 | 两种都选齐 |
| 找历史摘要、读颜色限制、据此生成 | 只选规则 | 三种都选齐 |
| 读规则→找参考→保存计划→生图 | 漏读规则 | 四种都选齐 |

这里验证的是**需要哪些能力**，没有验证工具先后次序、参数绑定、前一步输出是否正确传给后一步。[D5：`v2h2`、`v2h3`、`v2h8`、`v2h16`]

### 3.4 剩余错误不能略过

- **漏隐含前置读取**：比较两张画布卡片的说明，需要先读节点，V2仍漏选。能力描述偏查找/定位、没有明确读取用途，是下一轮假设，尚未做单因素验证。
- **已有参数却额外读规则**：直接生图任务，多选了规则读取。
- **已给节点ID却又搜索**：只删N-932时，多选画布查询，错误分数高达0.9977；提高置信度阈值不一定能解决。
- **拿相近能力冒充缺失能力**：没有取消工具时，仍为取消请求选了任务查询；用户已明确不要这样替代。
- **缺生成主题仍建议生图**：被缺参规则拦在建议层，不能算模型自己判断正确。

这些错误解释了为什么虽然召回明显提高，仍未通过预设的100%必要工具召回、零无工具误选等研究门槛。建议被拦住或没有执行，不会让原建议自动变正确。[S5、D5]

## 4. 画布关键词搜索、历史产物与规则检索

这部分测的是**给定来源和关键词后，对已找回的候选排序**，不是让分类器代替搜索引擎，更没有测试图片视觉内容。

| 来源 | 有答案查询首位命中：基线→重排 | 模型主动认出正确候选 | 无答案误接受 |
| --- | --- | --- | --- |
| 画布文字候选 | 1/4→4/4 | 4/4 | 1/2 |
| 历史产物文字摘要 | 3/4→4/4 | 1/4 | 0/2 |
| 已保存规则正文 | 1/4→4/4 | 4/4 | 0/2 |
| 合计 | 5/12→12/12 | **9/12** | **1/6** |

12/12中有3题是分类器没给出匹配建议、保留原排序，而原第一条恰好正确。这3题都是历史产物查询。因此只能说组合排序达到12/12，不能说模型独立匹配100%。给出的10个首位匹配建议中，9个正确、1个错误。

错误例子：候选只是临时文件名写“无反光”，正文明确实际效果未知，模型仍认定满足无反光条件。它说明**名字含关键词不等于有事实证据**。

这一轮没有扩大候选池，没有测试原本搜不到的记录能否召回，也没有改关键词解析、索引、分页或生产检索。因此不能宣称“画布搜索整体准确率100%”。每来源只有4个有答案和2个无答案场景，样本很小。[S3、D3]

## 5. 速度、token与费用：没有隐藏收益

| 操作 | 每任务分类请求数 | 客户端新增耗时p50 | 能说明什么 |
| --- | ---: | ---: | --- |
| 六类意图判断 | 1 | 0.251秒 | 单次分类开销，不是取代Planner后的净收益 |
| 检索来源判断 | 1 | 0.247秒 | 来源选择仍有错误/回退 |
| 三候选重排 | 3，串行 | 0.779秒 | 有排序信号，但无答案时仍可能误接受 |
| 工具V1首次实验 | 8，串行 | 2.008秒 | 全量回退，目录实际未缩减 |
| 同题V1对照 | 8，串行 | 2.001秒 | 与下面V2才是同题比较 |
| 同题V2 | 8，串行 | **1.985秒** | 仅约16ms差别，没有明显中位数提速 |

V1/V2同题留出输入token为 **29,320→15,944，减少45.6%**。单次p50为249.17→247.67ms，每题p95为3.663→2.377秒。p95来自16个任务，不足以判定稳定尾延迟改进；未做重复运行或并发/缓存实验，不能把全部差距归给提示缩短。

生产中的净收益还需要比较：

`新增分类耗时 + 主模型选择/修正耗时 + 实际工具执行耗时`

与原流程的完整耗时。后两项本轮没测，所以**没有总提速倍率**。现在V2保留所有工具，工具schema实际缩减为0；结果里的“仅建议集schema估算”不是已经取得的节省。[D3–D5]

费用方面，报价端点当时返回输入/输出token单价0，但没有可核实的每请求报价，响应也没有提供费用头，未读取实际账单。**结算费用未知，不能说免费，也不能说已经降低总费用。** 后三份结果报告输入用量合计125,716 token；这是部分实验可加总的usage，不是五轮全部用量或账单。

共用严格响应解析器，检查标签与完整概率分布；没有新增依赖、数据库结构、生产Feature Flag或第二套运行时。本轮“改进”不是微调，也没有切换主模型、改变Ontology实体权威、权限、执行确认、生成或恢复语义。

验证记录：最新V2聚焦检查9/9通过、架构检查通过；候选重排当轮相关基线检查31/31通过。它们分别证明本地实现/契约，不替代真实模型质量与上线验收。**本次总报告整理没有重新运行开发测试或真实评测**；做了JSON计数核对、同题主指标独立复算、报告格式与链接检查。

## 7. 当前生产决策

| 使用位置 | 建议 |
| --- | --- |
| 替换总意图路由/Planner | 不采用当前实验配置 |
| 自动决定去哪个检索来源 | 不采用当前实验配置 |
| 候选重排 | 有继续研究价值；先解决无证据误接受，不直接上线 |
| 工具能力建议/排序 | V2是目前最有力的继续研究方向；保留完整目录，不赋予执行权 |
| 工具裁剪、调用参数、执行顺序、取消/删除/生图授权 | 不由分类结果直接决定 |
| 正式流量、影子模式、部署 | 尚未实施，也尚未通过准入 |

推荐职责边界是：服务端确定已注册且允许暴露的能力 → 分类器提供能力建议 → 主模型形成调用参数与步骤 → 原有校验、确认、幂等和恢复机制执行。这是拟议方向，不是已经接入的生产链路。若上游状态未知或存在独立可执行子任务，不能简单“全任务先澄清”。

## 8. 后续优先级与完成标准

1. **先解决少数明确质量缺口。** 隐含前置读取、已知ID避免多查、不支持操作不得拿相近工具替代、缺参不得过早生成。先独立复核标签，再用新留出题验收；不在已经看过的错题上补关键词并宣称泛化提升。
2. **再做完整调用链对照。** 比较主模型直接看目录与V2辅助选择，测参数有效率、步骤顺序、真实任务成功率、失败恢复和端到端p50/p95。涉及项目内容/私有Prompt外传时，另核对数据及目的地授权；本轮合成评测不自动覆盖。
3. **最后评估性能和接入。** 当选择质量和安全行为过门槛后，再评估减少分类次数、受控并发、缓存、按需加载等。8种合成工具已需8次请求，工具更多时调用成本不能忽略；没有实测前不承诺提速比例。

总判断：**已从“不适合直接做综合判断”推进到“能明显提高工具建议召回”，但还没走完“可靠选择→正确参数与执行→净性能收益→生产接入”的验证。最值得保留的是V2原子能力判断及职责分离，不是把95.2%包装成整个Agent的准确率。**
