# Epic 9.2 局部编辑界面层 · 已定决策

> 尚未写完整设计规格。本文只记录已经确认的取向，避免它们只活在对话里。
> **排在 Epic 13 第一刀之后实施**（用户 2026-08-26 决定）。

## 前置事实（已实测，非推断）

用现有蒙版原语对 gpt-image-2 打三次真实调用，逐张肉眼确认：

| 能力 | 结果 |
| --- | --- |
| Object Remove | ✓ 红方块干净消失，背景均匀无痕 |
| Background Replace | ✓ 主体原样保留，背景整片替换 |
| Expand / 外扩 | ✓ 接受「基准图自带透明区」并在其中作画，接缝不可见 |

因此方案文档原文「这些是 Provider 能力，当前模型不提供，**不是接线问题，写不出来**」**不成立**。
六项里只有两项真被模型能力挡住：**可编辑文本层**（光栅模型不产出文本图层）与
**Object Move**（需分割+补洞+合成三步编排）。**Upscale** 不在这条链上，需独立超分服务。

限定：实测用的是合成图（纯色底 + 硬边方块）。真实照片里**蒙版质量才是决定成败的东西**，
所以「成立」指原语与请求形状可用，不指任意照片都出得好。另：Background Replace 是换背景，
不产出带 alpha 的透明图。

## 三个模型的编辑接口不同（这是设计的枢纽）

| 模型 | 蒙版怎么传 |
| --- | --- |
| gpt-image-2 | multipart 里一等的 `mask` 字段（已接入） |
| Seedream 4.x | 独立 inpaint / outpaint 模式 + 蒙版；参数名随供应商而变 |
| nano banana（Gemini） | **没有 mask 参数**，语义蒙版（自然语言描述区域） |

`generationModels.mjs` 现在用 `supportsMask: true` 这个布尔表达能力，**不够用**——
它表达不了「用哪种方式支持」。而 `generationProvider.mjs` 现在「不支持就抛 INVALID_MASK」，
对 nano banana 会判错：它支持局部编辑，只是不吃蒙版字段。

## 已定决策

1. **第一版覆盖三项操作**：移除物体 / 替换背景 / 外扩。
2. **跨模型降级：蒙版当「视觉指针」**。没有 mask 字段的模型，把用户涂的区域合成成一张带高亮
   标记的副本作为第二张参考图，提示词写「移除高亮标出的物体」。界面行为跨模型完全一致。
3. **自由涂抹笔刷**，不是矩形。现有 `RegionMaskEditor.tsx`（129 行）只能拖矩形；真实照片里
   包住一个杯子的矩形会连周围背景一起重绘，换背景更是几乎没法用（主体很少是矩形）。
   服务端 `recipe.mask` 早已接受任意带透明通道的 PNG。
4. **方案 A：意图进配方，服务端适配器翻译**。领域层新增操作词表，界面产出
   `EditIntent { operation, mask, prompt?, expandTo? }` 随配方提交；翻译在各适配器里，
   提示词模板是领域层纯函数。

### 为什么不选「客户端把意图烘成蒙版+提示词」

那样服务端一行不改、gpt-image-2 立刻能用，但**意图被烧掉**，三个后果：

- **换模型重试做不到** —— nano banana 需要完全不同的输入形状（高亮副本 + 描述性提示词），
  而那个信息已经没了。选了三个模型，这个场景一定会发生。
- **血缘断了** —— Epic 9.2 验收要求「任一精修可回到父版本」，烘掉后 Artifact 上看不出这是什么操作。
- nano banana 的合成要挪到客户端重写一遍，而服务端 `imageOverlay.mjs` 已有
  `decodeRgbaImage` / `encodeRgbaPng` / `overlayMarkOnBase`（靠 `jpeg-js`，零新依赖），
  且 `composeMarkOverlayPng` 目前没有任何调用方。

## 为什么排在 Epic 13 之后

方案 A 要让 `generationProvider.mjs` 与两个新适配器都认这个意图词表，而那些翻译逻辑
目前无处安放。先拆再加，比反过来便宜。
