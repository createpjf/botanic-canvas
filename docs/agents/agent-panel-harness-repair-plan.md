# Botanic Agent 面板与 Harness 修复方案

日期：2026-09-05。范围：当前工作树，不代表线上版本。方案阶段后已按目标继续实施；以下约定仍是验收标准，实际进度以修复 Checkpoint 为准。

本方案针对普通用户完成创作的全过程，不以“接入了多少个 AI Elements 组件”作为完成标准。它补充已有修复进度记录，不替代运行时状态，也不自动授权提交、部署、迁移或付费生成。

## 1. 核心判断与完成目标

当前主要问题是：面板展示、对话控制、生成执行、结果索引和画布同步各自有状态，但用户看不到一条可靠的连续操作路径。

- 选择了图片，不等于模型实际收到图片或描述。
- 点了确认，不等于答案已可靠保存并接续同一次操作。
- 重试函数返回，不等于协作握手和待同步数据已完成。
- Run 完成，不等于该 Run 的结果已经进入当前已加载的 Artifact 页面。
- 显示一个“用时”或分隔线，不等于整轮已经完成。
- 单测或构建通过，不等于用户能够独立找到结果、继续修改并刷新恢复。

完成目标是：用户可以完成“进入项目 → 引用素材 → 提交要求 → 必要确认 → 看懂处理状态 → 看到真实结果 → 修改指定结果 → 中断后恢复”，不用理解 Turn、Run、Job、Outbox 或 Artifact Index。

## 3. 不可破坏的边界

1. Message 保存对话事实；Turn 管控制权与事件续读；Run 管已创建任务；GenerationJob 管生成执行；Artifact Index 管历史产物。UI 只投影，不建立第二套任务状态机。
2. 保持幂等身份、租约/fence、取消确认、未知结果、项目版本冲突、媒体授权和历史血缘语义。
3. 不修改 Provider 选择策略、Flock 请求格式、网络超时；不以更换模型掩盖上下文准备失败。
4. 不把模型原始 reasoning、图片字节、caption 原文、私有媒体地址或 Provider body 写入消息、计划、Run、Artifact 或新日志。
5. 不改 ReactFlow 主画布布局，不引入新 UI 库、测试框架或全站 token 重构。
6. 不清理无关改动；超限文件按已有行为边界收口，不提高 architecture 行数预算，不为拆文件新增空透传层。
7. 旧方案中“只有两个 UI 接口变化、完全没有数据库影响”不能直接套用到当前 Harness 修复。确认一致性涉及已有 Message 合并与 SQL 写路径，必须审查本地迁移的必要性和兼容性；没有必要就不保留额外机制。任何共享环境迁移单独授权。

## 4. 统一交互契约

### 4.1 一次操作只显示一个主要进度入口

| 真实状态 | 普通用户看到什么 | 允许的主要操作 |
| --- | --- | --- |
| 消息尚未可靠保存 | 发送中；失败时发送失败 | 重试发送，保留原身份 |
| Turn 已受理，但无可展示内容 | Bob + Shimmer“正在规划…” | 停止 |
| 引用准备出现问题 | 相应引用的简短状态 | 重试准备或移除无效引用 |
| 收到真实 reasoning | 当轮 Reasoning | 展开/收起；结束不持久化 |
| 收到工具或可展示进度 | 执行记录及当前动作 | 展开详情、停止 |
| 等待用户确认 | 当前确认卡，不再显示通用 Shimmer | 选择、确认；保留输入 |
| 已有可提交计划 | 可编辑 Plan，必要参数可见 | 修改、确认执行 |
| Run 排队/执行 | 排队中或生成中；已有结果可先展示 | 停止、查看任务 |
| 请求取消，尚未确认 | 正在停止… | 不提供会产生新计费尝试的普通重试 |
| 完成/部分完成 | 结果、简短结论、定位/继续修改 | 针对结果操作；部分失败单独处理 |
| 结果未知 | 正在核对结果或需核对 | 查看/恢复原任务，禁止直接重复生成 |
| 历史记录 | 正文、结果、折叠执行记录 | 查看；旧确认卡不可再次提交 |

“工具调用结束”“收到一条消息”“HTTP 结束”“Turn 等待确认”都不能直接推出整轮完成。已有明确内容时，通用 Shimmer 撤掉；具体任务自身的运行状态仍保留。

### 4.2 分隔线与用时的裁决

- 用户消息前不画分隔线。
- 当前轮未结束时不画完成分隔线，包括 waiting_user、等待取消确认和关联 Run 仍执行。
- 终态 Assistant 回复开始处最多一条分隔线，横跨内容区域，不做圆角卡片边框。
- 执行记录标题下面不再加一条与上述分隔线重复的横线。
- 折叠执行记录显示“用时 35 秒 + 箭头”；展开显示动作和详情。辅助名称可叫“执行记录”，不再叫“推理摘要”。
- 缺失时间显示“执行记录”或步骤“—”，不能用页面加载时间制造“<1 秒”。不相关的普通文本回复不强行生成一张空执行记录。
- 不删除用户或模型正文中合法的 Markdown 分隔线。

### 4.3 AI Elements 的职责固定

| 组件 | 在本产品中的职责 |
| --- | --- |
| Conversation / Message / MessageResponse / MessageActions | 消息滚动、左右布局、Markdown、通用操作 |
| Shimmer | 无内容等待状态；不是 reasoning |
| Reasoning | 经现有开关允许的当轮真实 reasoning；不持久化 |
| Chain of Thought / Tool | 安全执行摘要、步骤、用时、可折叠工具详情 |
| Checkpoint | 真实恢复记录；无恢复能力时不伪装按钮 |
| Plan / Confirmation | 提交前计划与必要的当次授权 |
| Task | 一个真实 Run 的任务管理入口 |
| Queue | 多个真实待执行/运行任务的概览；与输入草稿队列分开 |
| Attachments / Artifact | 消息内结果缩略图 / 结果详情，不能互相替代 |
| Inline Citation / Sources | 可核验来源；项目实体另用可定位标签 |
| Prompt Input / ModelSelector | 输入、引用、模型与发送；领域逻辑仍由现有模块拥有 |
| Context | 仅真实 token/context usage；不用于“已引用”托盘 |

不引入官方 Canvas、Voice 或静态 Agent 卡来解决本轮问题。已有组件无需机械同步成最新版。

### 4.4 展示接口与所有权

以下是本地展示契约，不是新数据库 schema；能从既有值推导就不增加字段或状态容器。

| 契约 | 最小实现方向 | 不允许 |
| --- | --- | --- |
| 确认是否可操作 | 在现有确认投影中结合消息、对应 Turn、Plan/Run 的真实身份；区分待确认、已保存待接续、历史、暂不可恢复 | 单靠卡片位置、正文、客户端时间或全局 planning 判断 |
| 引用采用反馈 | 复用当前 attempt 的安全事件；仅携带引用 ID、阶段、采用模式、原因代码 | 持久化图片/caption/私有 URL，或另建引用任务状态机 |
| 同步重试 | 保留 `onRetryRealtimeSync` 入口；拒绝可解释错误，真实完成由现有协作状态/Outbox ACK 判断 | resolve 即标成功，缺实例时静默 no-op |
| 结果读取 | 在现有 Artifact 协调器保留 cursor、首次/更多读取错误与已加载结果；向消息传递足够的读取范围信息 | `ready` 等于全项目索引穷尽 |
| 继续修改 | 入口绑定用户选中的 Artifact/当前有效节点；由既有领域逻辑解析目标 | 没找到输出就无提示地改用旧引用 |
| 分隔线/头像 | 先得到实际可见消息及真实终态，再由同一消息展示入口决定 | 各层 CSS 或各卡片分别画完成线、占用最新 Bob |

涉及共享协议时，只扩展已有安全事件并同步必要类型/生成物；涉及 ProductStore 写入则三个 Adapter 同步验证。不能继续套用“本轮最多只改两个 UI prop”的旧估算。

## 5. A：确认、消息持久化与历史恢复（P0）

目标：同一次确认只产生一次有效接续；刷新、网络重试、客户端时钟偏移和多设备竞争不改变用户已经确认的事实。

### A0：项目进入与刷新恢复前置检查

此项属于 A 的验收前置，不新增第十个修复包，也不扩大到 ReactFlow 布局。

主要入口：`src/features/canvas/CanvasWorkspace.tsx`、`src/features/canvas/useCanvasWorkspaceSynchronization.ts`、`src/store/canvasDocumentLifecycleActions.ts`、`src/lib/db.ts`。先复用现有项目打开/刷新 E2E 与 `project.open` 观测，不建立第二套初始化器。

1. 固定同一源码/构建、API、持久化模式与项目，分别记录首次进入、hash 深链刷新、从项目列表进入。前台活跃页面和后台标签分别核对，排除运行环境造成的计时/页面差异。
2. 逐段观察 hydrate 完成、openDocument 返回、当前路由项目与 Store document.id 一致、恢复遮罩退出。只记录阶段、耗时及安全错误码，不读取浏览器私密会话存储或打印用户内容。
3. 验证已有 45 秒兜底覆盖真实阻塞分支、不会因 effect 重启反复计时；document mismatch 不能绕开兜底永久停留。只有复现后才调整对应 effect、生命周期或存储入口，不预判是哪一层错误。
4. 失败必须出现可操作的“重试 / 返回项目”；错误详情进入辅助信息。不可把强设 hydrated、忽略项目身份、清空 IndexedDB/Outbox 当作修复。
5. 切换项目后旧请求不得覆盖新项目；重试不重复新建项目、会话、Turn 或 GenerationJob；已有本地草稿与待同步修改保持可恢复。

验收：同构建页面从列表进入与深链刷新均可到达正确项目；人为挂起/失败的读取在既有等待边界后能退出或明确重试；快速切换项目无串页、无数据清除。原因未查明时，只记待诊断，不把 UI 文案改动记为恢复完成。

### A1：确认接续与历史卡

主要入口：[确认提交](../../src/features/agent/agentClarificationSubmission.ts)、[请求快照](../../src/features/agent/agentComposerState.ts)、[消息交付](../../src/features/agent/useAgentMessageDelivery.ts)、[消息队列](../../src/lib/agentMessageQueue.ts)、[读模型](../../src/domain/agentMessageReadModel.ts)、[服务端合并](../../server/agent/thread/agentMessageMerge.mjs)。

实施要求：

1. 当前卡只允许一次在途提交；按钮显示“提交中…”，失败保留选择并显示可重试错误。不能只靠禁用按钮处理跨设备竞争。
2. 确认消息和答案 Message 保存成功后，使用服务端实际返回的内容、时间和身份继续；不使用乐观本地答案覆盖服务端已经采用的答案。
3. 检查真实持久化回执边界：HTTP 成功但回执缺失、身份不符或无法验证时，不标记已可靠保存、不继续执行、不丢队列项。已演进为 Plan/Run 的权威回执不重复提交一次旧确认。
4. 同一稳定操作的网络重试复用已有身份；用户明确重新发起才创建新操作。已经确认的不同答案走现有冲突语义，不做“客户端时间更新者覆盖”。
5. 历史卡只读必须来自真实关联：sourceMessageId、turnId、resolvedGeneration、关联 Run/Plan。当前可操作确认要与对应 Turn 的待确认问题匹配；已保存但尚未接续时只提供接续，不让用户修改已经采用的答案。不能因为项目里随便有一个新 Run 就把所有确认卡标成完成。
6. 原始请求未在当前消息页时，复用消息分页接口做有界查找；重复游标、切换会话/项目立即停止接续。达到查找上限时提供“加载更早消息”，不能无限扫描。
7. 恢复只用原快照的模型、执行模式、引用、目标和技能。缺必要信息就说明“原请求设置不完整”，不借用当前 Composer。原快照中没有技能代表未挂载，不自动添加今天的新技能。
8. 切换会话后晚到的保存/分页响应可以更新正确实体，但不能抢切当前会话、清空新草稿或执行旧确认。
9. Local/PostgreSQL/Supabase 合并规则保持一致。对已有 SQL 变更验证完整直接 PUT 和兼容同步 RPC、参数签名、权限及迁移缺失时的 fail-closed，不止测试 helper 文本或单个 SQL 函数。
10. 缺关联的历史卡不能默认恢复成可执行 pending。先按现有只读接口查询所属操作；关联和原请求快照均无法确认时，只保留历史查看及明确的“重新发起”入口。重新发起是用户授权的新请求，不伪装成重试，也不自动补写历史关联。
11. 保留新加的本地原请求快照和确认卡身份复用；验证本地、定稿 Prompt 与服务端 Turn 三条入口都遵守同一提交契约。历史不可恢复卡不得阻断用户后续的明确新请求，也不得让简短“直接生成”回退到另一条旧 Prompt。
12. 接续失败的重试仍携带原 sourceMessageId、clarificationMessageId 与原快照，不能因答案 Message 排在后面就把答案当作新的生成要求。已保存的确认答案、最终计划和用户消息按关联呈现，不能留下两个可操作确认入口。
13. “重新填写”只回填原指令供用户核对，保留当前草稿替换确认；必须再次提交才构成新请求。找不到原快照时不静默采用当前图片、模型或技能，也不自动发起生成。

当前页面的旧卡问题先区分三种情况：旧记录缺少身份、当前投影漏掉已有关联、预览/API 版本不一致。只有复现对应情况后才改该层；不预设需要新 rootTurnId 字段、数据回填或改变现有 Turn 身份算法。

验收：确认 → 保存后刷新 → 恢复同一操作；两设备提交同题相同/冲突答案；客户端时间领先；原请求在历史页；缺快照；回执缺失；切换会话。业务效果不重复，历史卡只读，草稿不丢。必要并发和 Adapter 契约可超出普通局部修复的测试数量上限，但不新增测试框架。

## 6. B：引用与真实视觉上下文（P0）

目标：用户知道引用是否可用；系统不把“UI 中有缩略图”说成“模型已经看见图片”。

主要入口：[视觉准备](../../server/agent/semantic/botanicAgentVision.mjs)、[Turn 编排](../../server/agent/turn/botanicAgentTurn.mjs)、[Chat 通道](../../server/agent/semantic/botanicAgentChat.mjs)、[Composer](../../src/features/agent/AgentComposer.tsx)、[请求协调](../../src/features/agent/AgentWorkspace.tsx)。

实施要求：

1. 区分四个事实：已选择、准备成功、已放入实际请求、准备/采用失败。准备好了但该 attempt 没有提交，不能显示“已采用”。
2. 沿现有安全事件/请求投影传递有界元数据：当前 attempt、引用实体 ID、阶段、采用模式与失败原因代码。只在必须时扩展现有协议并更新生成物检查，不新增数据库表或调试日志系统。
3. 原生视觉和 caption 降级分开表示：模型收到图片与模型只收到图片描述，不使用同一句“已看图”。不暴露 caption 原文、data URL、签名 URL 或 Provider body。
4. 严格按当前候选数、媒体大小和已有准备上限选择；当前实现最多 4 张、总图片字节上限 16 MiB，本轮不擅自提高。超限引用不得静默失踪。默认收起状态中保留简短异常提示，展开后定位到具体引用。
5. 指定“这张图”“继续修改该结果”等依赖目标图片的任务，目标准备失败时停止该执行路径并提示恢复；不能改成对其他成功图片或纯文字继续猜。
6. 非目标型请求允许已有降级策略，但须明确哪些引用没有采用。部分失败只重试准备失败的引用，不重新生成已有结果。
7. vision/text fallback、恢复 attempt 和事件重放有明确归属；已放弃 attempt 的晚到状态不能覆盖当前 attempt。会话/项目切换时不串图、不串状态。
8. 未配置视觉能力、媒体无权限、已删除、格式不支持、网络失败分别提供最小必要提示。权限失败不能通过泄露私有 URL 或绕过授权“修复”。
9. 引用是否可恢复以既有服务端项目归属、媒体读取与 Job 输出解析为准；浏览器缩略图暂缺不能单独证明原媒体不存在。避免前端预检查错误拦住服务端本可恢复的目标；也不能因历史 Artifact 存在就绕过当前访问权限。

验收：两张图片一张失败；引用超过准备上限；指定目标失败但旁图成功；原生视觉失败后 caption 降级；取消/切换会话时结果晚到。界面状态与实际构造的请求一致，而非只与候选列表一致。自动化使用现有 Provider mock，不付费调用。

## 7. C：画布同步与真实重试（P0）

目标：重试有实际动作、有明确反馈，不把“重新尝试”显示成“已经同步成功”。

现状：共同入口已修复缺实例空成功与错误未投影，并通过聚焦检查。底层 retry 返回仍只表示发起重试，不代表握手/Outbox 已被确认；真实恢复闭环仍须验证。执行桥接应核对 reconnecting/syncing/blocked 三种写入受限状态，与 Store 已有写保护保持一致，不能只覆盖 reconnecting。

主要入口：[同步协调](../../src/features/canvas/useCanvasWorkspaceSynchronization.ts)、[共同重试](../../src/features/canvas/canvasRealtimeRetry.ts)、[协作客户端](../../src/lib/projectCollaboration.ts)、[Agent 头部](../../src/features/agent/AgentWorkspace.tsx)、[执行回写](../../src/features/canvas/useCanvasAgentExecutionBridge.ts)。

实施要求：

1. 复用 realtime retry，不接到本地草稿 persistence retry。没有有效协作实例时提供可解释错误或现有重新连接入口，不静默成功。
2. 头部“同步受阻 · 重试”触发后显示“正在重试…”，避免重复请求；依据协作状态的真实后续变化退出，而非单凭 Promise resolve。
3. 连接恢复但 Outbox 未确认时仍显示同步中；握手成功不等于所有本地修改已经保存。
4. 使用现有失败分类区分网络/握手、权限、版本/epoch 和本地保存问题；仅提供该错误允许的恢复动作。不新造 UI 判断去绕过底层协议。
5. 失败保留重试入口与短原因；详细内容放辅助文本或 tooltip，头部不塞长段解释。
6. 按操作能力保护：不能写画布时禁用相关写操作；执行桥接保留已完成结果及 canvasWritebackPending，不对 Store 已明确拒绝写入的状态反复创建节点。连接恢复后只续写未确认部分，既有写回回执不重放，不重新生成。是否能继续文本对话仍取决于其自己的服务和项目权限，不一律屏蔽，也不一律放行。
7. 重试不清空草稿、不丢 Outbox、不自动重新生成、不重新提交已确认 Run；切换项目后旧响应不修改新项目状态。

验收：有实例/无实例；临时断线恢复；权限未恢复；握手已恢复但 Outbox 仍等待 ACK；切换项目。不得出现无实际动作的绿色成功状态。

## 8. D：有效默认值与必要确认（P1）

目标：普通单图请求不必反复回答已有合理默认值的问题，但费用、批量、外部行动和不明确的目标仍受保护。

已核对：当前自动模式会补全默认创意 brief，手动模式仍可能连续询问比例/用途、清晰度和优化方向。执行模式与参数完整性被耦合。

主要入口：[创意 Brief](../../src/domain/agentCreativeBrief.ts)、[指令路由](../../src/domain/agentInstructionRouting.ts)、[Plan 展示](../../src/features/agent/AgentConversationMessage.tsx)。

实施要求：

1. 手动/计划模式同样可以使用有效默认值；“使用默认值”不代表“自动授权执行”。
2. 新请求的参数优先级：本次明确要求/确认 → 当前明确选定设置 → 适用的目标/项目上下文 → 所选模型支持的默认值。冲突不可静默覆盖；恢复旧请求则遵守 A，不重新套当前默认。
3. 已能生成安全 Plan 的比例、分辨率和优化方向，直接在 Plan 中可见、可改；不先做一套问卷再展示同一套参数。
4. 只询问阻断任务的问题：目标不明确、缺必需素材、用户要求互相冲突、不支持的参数，以及需要当次授权的动作。
5. 手动模式保留最终执行确认；计费、批量张数、外部工具和模型推断出的生成意图遵守现有策略。默认补参不能顺手增加确认豁免。
6. 区分对话模型与生成模型；显示用户可理解的名称及当前有效模式。不能用一个图标让用户误以为所有阶段都使用同一个模型。
7. Plan 提交后成为只读记录；要修改已创建任务的条件，通过已有重新编辑/新计划流程，不篡改旧 Run 的原始计划。
8. 用同一测试请求核对用户选定参数 → 已确认 Plan → GenerationJob 的实际参数；模型不支持时在确认前说明，不出现界面显示 2K、实际偷偷提交 1K 的降级。当前历史页面不能单凭相似图片认定它们属于同一请求，此项须按真实关联验证。

验收：明确单图请求直接到可编辑 Plan；用户明确比例/模型不被覆盖；不支持参数才询问；批量及外部工具仍确认；刷新恢复仍用原设置。复跑现有意图路由/eval，防止把闲聊变成生成。

## 9. E：结果闭环、历史分页与任务可辨认性（P0）

目标：任务完成后，在对应对话直接看见真实结果，并能准确修改其中一张；历史结果不会因为未加载而被误判不存在。

主要入口：[消息结果](../../src/features/agent/AgentConversationMessage.tsx)、[Artifact 协调](../../src/features/canvas/useCanvasAgentExecutionBridge.ts)、[结果面板](../../src/features/agent/AgentUtilityPanels.tsx)、[任务面板](../../src/features/agent/AgentTaskPanel.tsx)。

实施要求：

1. 保留已有 run/notice 统一关联判断与同 Run 最新消息去重；所有结果、持续时间和操作入口使用相同关联，不在其他分支再依赖 kind。
2. 只从 Artifact 的真实 provenance.runId 和相关实体读取结果，不从最新画布图片或旧上下文拼一组“本次结果”。
3. 修正分页语义：当前 ready 只代表当前页已加载，不代表历史穷尽。首页 100 项之外的 Run 不能直接显示“未找到结果”。
4. 复用现有分页读取，按当前可见/用户请求的结果范围有界加载；仍有更早页时提供加载入口。没有覆盖目标范围之前使用“结果尚未载入”，不做全项目无限抓取或每条消息一个新 API。仅按 Run 创建时间不能证明已经穷尽其 Artifact；存在后补写入时尤其不能如此推断。
5. 区分首次读取失败和加载更多失败；保留已有结果和失败游标，重试同一读取动作。索引失败绝不触发生成重试。
6. 同 ID 的 Artifact 更新不能被“Map 中已存在就忽略”吞掉；按现有版本/更新时间或明确响应合并规则接受权威更新，同时防止迟到旧页覆盖较新状态。
7. 图像任务的 completed/partial + artifacts：执行记录 → 缩略图 → 简短结论 → 结果操作。部分成功立即保留成功图片，并单独展示未完成分支。
8. 对确实没有媒体输出的任务，不要求凭空显示图片；对预期有媒体、索引范围已确认且无产物的成功 Run，显示“未找到结果”及查看任务，不把缺图说成已成功出图。
9. 定位前验证画布节点仍存在。节点已删但 Artifact 尚存：仍可预览/下载，不显示无效“定位”；重新放回画布仅在现有授权能力允许时提供。
10. 多图的“继续修改”必须明确目标：单张直接选中，多张先选择或使用每张菜单。不得默认把全部输出连同历史引用一起加入，造成“改这张”改成其他图。
11. Task 用可读任务目的、真实状态、创建时间、结果预览和来源会话区分；不是满屏“已完成”。一个 Run 一个 Task，保留筛选、取消、分支恢复和来源入口。
12. 打开任务/结果面板后返回，恢复原会话、滚动位置、焦点、草稿及引用。只保存 UI 导航位置，不复制任务事实。

结果缺失展示须区分：正在读、分页未覆盖、读取失败、当前读取快照已穷尽且无结果。Run 刚终态但索引尚未同步时复用现有刷新/回写观察；超过既有等待边界仍没有结果才显示可诊断缺失，不永久转圈。不得创建一份浏览器“补图结果”冒充 Artifact 写回完成。

验收：notice 终态、单图、多图、部分完成、历史第 101 项以后、加载更多失败、Artifact 原位更新、画布节点删除、指定一张继续编辑及返回聊天。没有重复卡、错误图片或空定位。

## 10. F：停止、失败与恢复动作（P0）

目标：失败发生在哪里，那里就有正确恢复入口；停止从 Turn 到 Run 的交接不断档，不制造重复计费。

主要入口：[回合恢复](../../src/features/agent/agentTurnRecovery.ts)、[动作生命周期](../../src/features/agent/useAgentActionLifecycle.ts)、[消息与任务恢复入口](../../src/features/agent/AgentTaskPanel.tsx)、[执行桥接](../../src/features/canvas/useCanvasAgentExecutionBridge.ts)。

| 失败/中断类型 | 恢复动作 | 禁止动作 |
| --- | --- | --- |
| Message 未可靠保存 | 重试发送同一 Message | 先执行后补保存 |
| 观察连接断开 | 从原 Turn 事件游标继续观察 | 创建新 Turn 冒充恢复 |
| 已有明确可重试工具失败 | 原工具/任务允许的重试 | 重放整段成功过程 |
| 某个生成分支失败 | 重试该失败分支 | 重跑成功分支 |
| 取消尚未确认 | 继续观察取消状态 | 立刻显示已停止或允许重复生成 |
| Provider 结果未知 | 核对/恢复原任务 | 普通重试直接创建新计费尝试 |
| 仅 Artifact 读取失败 | 重试索引读取 | 调用生成 API |
| 同步或权限受阻 | 对应连接/权限恢复 | 清空本地数据或绕过权限 |

实施要求：

1. UI 恢复操作由现有错误代码和运行状态决定，不仅依据 message.status === failed 显示同一个“重试本轮”。
2. 提交前、accepted 前、Turn 执行中、关联 Run 创建后都保留同一停止意图；沿用 sticky cancellation 和 fence，不引入仅存在内存中的停止标记作为权威。
3. “正在停止”直到权威终态/取消确认；请求取消失败时保留明确操作，不吞异常。
4. 输入队列与任务队列区分；失败/取消后不能因队列自动推进悄悄提交后续付费任务。保留现有明确的自动推进规则，审查其是否与用户当前模式一致。
5. 刷新恢复先读已有 Turn/Run/Job，再决定是否允许重试；晚到的旧 attempt 不能覆写新的 activeJobId 或清除已有成功结果。

验收：Stop 在 accepted 前后和 Run 刚创建时各可生效；观察断线不重复执行；未知结果不能普通重试；部分失败只重试失败部分；取消刷新后仍保留停止意图。

## 11. G：执行记录、时间与可核验引用（P1）

目标：过程有用但不抢占答案；用时可信；引用能点击、能核验，不误删正文。

主要入口：[时间线 Hydration](../../src/features/agent/agentTurnTimelineHydration.ts)、[用时](../../src/domain/agentTimelineTiming.ts)、[工具折叠投影](../../src/domain/agentToolAccordion.ts)、[来源](../../src/components/AgentWebSourcePills.tsx)、[引用交互](../../src/components/ai-elements/inline-citation.tsx)。

实施要求：

1. 每步固定显示动作、必要状态、用时；参数/输出/错误在展开内容中。安全 why 可作为一句动作说明，不另标“为什么”或“决策轨迹”。
2. 单步用服务端事件/Job 的真实开始结束时间；整轮用同一操作的真实边界。并行步骤用时不简单相加；等待确认时间与执行时间不能混称“思考时长”。
3. hydration 只读重建，不因加载发生在今天而把历史结束时间设为今天，也不把一次批量读取压成“<1秒”。缺结束事件且页未读完时标未知/待载入，而不是完成。
4. 运行、失败、需确认在进入该状态时自动展开一次；成功默认折叠。用户手动展开/收起优先于后续 tick、重渲染和相同状态事件；不能每秒抢回展开状态。
5. 工具连接线仅连接相邻步骤，最后一步无尾线。真正的 Checkpoint/恢复动作才显示恢复记录，不把工具的 reexecute 策略当成可点击恢复点。
6. 生产只显示有界安全摘要；原参数、receipt ID、Provider body、策略字段不能混进普通 UI。开发技术详情也只读取已经脱敏且被允许的数据，不能以开发模式绕过安全边界。
7. 保留当前完整 URL 去重：hostname 只用于标签，有有效 URL 时用 URL 身份；不同路径/必要查询参数不能合并。只按现有安全规则规范化，不擅自删掉有语义的 query。
8. 正文与 timeline 来源建立唯一最终来源投影；步骤展开可显示自己的证据，最终答复末尾只出现一组。无可见“来源”标题，但保留可访问名称。
9. 项目来源按实体 ID 去重，可定位且名称来自实体；普通字符串与“项目本体”不能自动伪装成可定位实体。role/provider 等元数据从结构化渲染入口控制，不用宽泛正则删掉用户正文中的括号内容。
10. 当前引用卡基于 HoverCard；验收点击/触屏与键盘，必要时复用已安装的可点击 disclosure/popover。不能只有 hover 才能读详情，展开内链接必须可聚焦，Esc/关闭恢复焦点。
11. 原始 reasoning 仅在 AGENT_RAW_REASONING 允许时当轮展示，结束/切换后清除，历史不恢复原文；执行摘要不冒充原始思维链。

验收：历史事件有时间/缺时间/分页不完整；并行执行；手动折叠后持续更新；同域不同 URL；真实项目实体；触屏打开来源；正文含合法 role 文本不误删；无原始 reasoning 落库。

### 13.5 发布与回滚边界

1. 本地代码、测试、浏览器验收先完成；提交、推送、部署和共享数据库迁移分别核对授权。
2. 若确认一致性 SQL 保留，先检查新旧客户端/API 的 RPC 兼容矩阵与迁移顺序，在可恢复的 staging 环境执行；不要按“纯 UI 发布”处理。
3. Staging 核对前端/API/Worker revision，执行文本、引用、受控图片、确认刷新和恢复链路；图片验证须有明确的次数/费用授权。
4. 逐一核对 Run → GenerationJob → Canvas 节点 → Artifact Index → 对话附件，不把只在画布出现图片当作闭环完成。
5. 生产仅在 staging 通过且发布条件具备后进行；核对真实部署 revision、Agent API、Worker、Artifact 读取和浏览器异常。
6. 纯样式/投影回归可回滚前端；涉及 Message 合并或 RPC 的修复不能承诺“只回滚前端就足够”。按兼容矩阵回滚对应 API/前端，保留已确认消息、Run、Job 与 Artifact，不破坏性撤销已有用户数据。

## 14. 最终交付标准

- 功能：输入、确认、结果、编辑、取消、恢复各有可靠闭环。
- 信息：用户能知道用了哪些引用、正在做什么、是否需要操作、结果在哪里。
- 视觉：不再靠一次次局部 CSS 覆盖修双线、空白、缩进和按钮漂移。
- 代码：保留已有权威状态与模块职责，公共规则在共同入口修复，领域逻辑不塞进共享 UI。
- 证据：每包有 Checkpoint；全量门禁、浏览器、staging、生产分别记录；已实现、已验证、已上线明确区分。

这轮完成的判断不是“组件像 AI Elements”，而是普通用户不需要了解内部系统也能独立完成一次可靠创作。
